## 1. Décisions principales

1. **L'identité d'un topic est `primary_topic.id`, jamais son libellé.**
2. **Le détecteur ne fait aucun threading sémantique.** Un même ID OpenAlex est suivi dans le temps ; un changement d'ID ou de taxonomie est un événement de données, pas un mouvement scientifique.
3. **Le headline n'exige pas d'abstract.** OpenAlex peut attribuer un topic à partir du titre, du journal, des citations et, lorsqu'il existe, de l'abstract.
4. **Le type `article` seul est trop restrictif.** Les types sont organisés en flux documentaires explicites et ne sont pas tous mélangés.
5. **Le périmètre institutionnel est un paramètre versionné.** `exact`, `lineage` et `curated_set` correspondent à trois questions différentes.
6. **Les fenêtres comparées ont toujours la même durée.** Un semestre incomplet n'est jamais comparé directement à une année complète.
7. **Les counts et les parts de portefeuille sont calculés ensemble.** Une hausse absolue due à la croissance générale de l'institution ne vaut pas automatiquement gain de momentum.
8. **Le détecteur sépare présence, direction et accélération.** `NEW`, `RISING` et `ACCELERATING` ne décrivent pas la même propriété.
9. **Le signal est calculable sans LLM.** Les modèles génératifs n'interviennent qu'après le déclenchement, dans le drill-down éventuel.
10. **Chaque exécution conserve son manifeste de requête et son vintage de données.**
11. **La détection est multi-échelle (topic + subfield + field), le topic restant l'unité de sens.** Mesuré sur le run Mines `lineage` (voir `06_topic-granularity-diagnostic.md`), le grain topic est dans le régime des petits effectifs — 82 % des topics actifs portent moins de 3 œuvres dans la fenêtre courante et 66 % des onsets `RISING` se retournent à +12 mois. Monter au subfield stabilise (retournement 66 %→43 %) mais efface les pivots fins et laisse 40 % des subfields actifs sous 3 œuvres. On ne choisit donc pas un niveau : le classificateur tourne aux trois niveaux et le subfield/field sert de **couche de corroboration** au signal topic, pas de remplacement.

## 2. But du détecteur

### Question

> Quels topics prennent ou perdent une place inhabituelle dans l'activité récente d'un univers de recherche, par rapport à son propre historique ?

### Sortie

Pour chaque topic éligible, le détecteur produit :

- une série de volumes ;
- une série de parts dans le portefeuille ;
- une présence récente et historique ;
- un delta entre fenêtres homogènes ;
- une direction ;
- une accélération éventuelle ;
- une anomalie par rapport à la baseline ;
- une confiance ;
- un dossier de preuves minimal ;
- un objet `TopicMomentumSignal` versionné.

### Non-objectifs

Ce détecteur ne répond pas à :

- l'institution est-elle en avance sur le monde ? → détecteur de positionnement ;
- les citations d'un article accélèrent-elles ? → détecteur citationnel ;
- une méthode migre-t-elle entre domaines ? → détecteur sémantique futur ;
- que disent exactement les publications ? → drill-down de contribution frames/claims ;
- la production est-elle de meilleure qualité ? → aucune inférence de qualité à partir du volume.

## 3. Constat sur les fichiers existants

### 3.1 `mines_corpus(2).json`

Le digest contient des œuvres regroupées par fenêtre avec :

- `id`, `title`, `date`, `year` ;
- `abstract` ;
- `topic` et `field` sous forme de libellés.

Champs manquants pour le contrat :

- `primary_topic.id` ;
- hiérarchie topic complète ;
- type documentaire ;
- institution(s) ayant provoqué l'inclusion ;
- mode de périmètre institutionnel ;
- `updated_date` OpenAlex ;
- manifeste de requête ;
- couverture des topics ;
- vintage de collecte.

### 3.2 `topic_delta_table(1).json`

La structure `topic / prior_2025 / recent_2026H1 / total` est utile comme vue de présentation, mais insuffisante comme sortie canonique :

- le topic n'a pas d'ID ;
- les fenêtres ont des durées différentes ;
- aucun dénominateur ne permet de calculer la part de portefeuille ;
- aucun seuil, niveau de confiance ou manifeste de corpus n'est conservé ;
- la structure ne distingue pas présence, direction et accélération.

### 3.3 `mines_delta(2).json`

Ce fichier décrit des clusters de claims `NEW/PERSISTING/DISAPPEARING`. Il ne constitue pas une entrée du détecteur Topic Momentum. Il reste une source méthodologique pour le talk et un éventuel drill-down ciblé.

### 3.4 `persist(1).py`

Le module :

- calcule des centroïdes de clusters de claims ;
- chaîne ces clusters par similarité cosinus ;
- produit une trajectoire à partir de `n_papers` et `n_claims`.

Cette logique est pertinente pour des thèmes sémantiques sans identité stable. Elle ne doit pas être appliquée aux topics OpenAlex, qui possèdent déjà un ID. Les parties potentiellement réutilisables sont limitées à :

- l'idée d'un store par sweep ;
- l'alignement sur un axe temporel commun ;
- la production Markdown/JSON ;
- la séparation direction/accélération.

### 3.5 `client.py`

`map_records()` impose actuellement une longueur minimale d'abstract. Ce mapper est adapté au pipeline de claims, pas au headline Topic Momentum. Il faut un chemin distinct sans `min_abstract`, conservant `primary_topic`, `type`, `authorships`, `updated_date` et la provenance.

Le fichier reçu mappe des résultats OpenAlex mais ne contient pas la fonction de requête OpenAlex elle-même. Ce n'est pas bloquant pour le contrat, mais le futur raccord devra vérifier le comportement exact du connecteur `search-works-openalex`.

### 3.6 `kb_emitter(1).py`

L'émetteur est spécifique aux claims et à leurs membres. Le principe « un objet de signal traçable vers ses preuves » est réutilisable ; le schéma des clusters ne l'est pas.

## 4. Périmètre institutionnel : contrat explicite

### 4.1 Résolution initiale

Le ROR fourni par l'utilisateur est résolu une fois vers un OpenAlex Institution ID :

```text
ROR 04y8cs423 → OpenAlex I70768539
```

Le manifeste conserve les deux identifiants ainsi que le nom observé.

### 4.2 Trois modes

#### `exact`

Filtre :

```text
authorships.institutions.id:I70768539
```

ou l'équivalent ROR exact :

```text
authorships.institutions.ror:04y8cs423
```

Interprétation : une affiliation a été normalisée directement sur l'entité Mines Paris–PSL.

Avantage : périmètre strict.

Limite : exclut les œuvres affiliées uniquement à un centre descendant.

#### `lineage`

Filtre :

```text
authorships.institutions.lineage:I70768539
```

Interprétation : au moins une affiliation correspond à Mines ou à une institution dont la lignée contient Mines.

Avantage : meilleure couverture des centres de recherche.

Limite : le périmètre dépend de la hiérarchie OpenAlex/ROR courante et peut inclure des unités conjointes dont l'attribution institutionnelle doit être discutée.

#### `curated_set`

Filtre :

```text
authorships.institutions.id:I70768539|I4210115519|I4210108605|...
```

Interprétation : liste figée et versionnée d'entités admises dans l'univers.

Avantage : compromis recommandé pour un produit institutionnel reproductible ; les inclusions et exclusions sont explicites.

Limite : les nouveaux centres ne sont pas ajoutés automatiquement ; une nouvelle liste crée une nouvelle version de l'univers.

### 4.3 Mode recommandé

- **POC exploratoire :** `lineage`, avec `exact` calculé comme analyse de sensibilité.
- **Produit institutionnel :** `curated_set`, initialisé à partir de `lineage` puis validé par l'institution.

### 4.4 Snapshot de hiérarchie

À chaque changement de version d'univers, conserver :

- l'Institution ID racine ;
- tous les descendants inclus ;
- leurs ROR, noms, types et statuts ;
- la date de résolution ;
- les exclusions manuelles et leur justification ;
- une empreinte déterministe de la liste triée d'IDs.

### 4.5 Mesures Mines au 28 août 2026

Période : 2020-01-01 → 2026-06-30, corpus OpenAlex `core`.

| Requête | Œuvres |
|---|---:|
| Exact, tous types | 3 547 |
| Lineage, tous types | 12 658 |
| Exact, articles | 1 689 |
| Exact, articles avec abstract | 1 172 |
| Lineage, articles | 5 223 |
| Lineage, articles avec abstract | 3 664 |

Conséquences :

- `lineage` multiplie le corpus total par environ 3,6 ;
- sur les articles exacts, `has_abstract=true` retire environ 31 % des œuvres ;
- sur les articles en lineage, il en retire environ 30 %.

La hiérarchie `lineage:I70768539` contient actuellement 23 institutions, Mines incluse. Cette liste doit être archivée, car une modification de la hiérarchie changerait rétrospectivement le périmètre d'une requête live.

## 5. Population bibliographique : plusieurs flux

### 5.1 Pourquoi ne pas utiliser tous les types ensemble

Les disciplines n'emploient pas les mêmes supports et leur composition peut évoluer. Mélanger articles, preprints, datasets, logiciels, thèses et résumés de conférences peut produire un faux momentum uniquement causé par un changement de type documentaire.

### 5.2 Flux `published_core` — défaut du POC

Types :

```text
article
review
conference-paper
book
book-chapter
data-paper
software-paper
report
```

Justification : couvrir les principaux résultats scientifiques publiés dans les sciences, l'ingénierie et les SHS sans intégrer les objets les plus instables ou périphériques.

### 5.3 Flux séparés futurs

| Flux | Types | Usage |
|---|---|---|
| `preprints` | `preprint` | Signal avancé, avec risque de doublon/version |
| `research_objects` | `dataset`, `software` | Translation et diffusion de ressources |
| `dissertations` | `dissertation` | Formation/recherche doctorale |
| `editorial_context` | `editorial`, `letter`, `book-review` | Analyse éditoriale spécifique |
| `quality_events` | `erratum`, `retraction` | Vigilance, jamais volume principal |
| `excluded_noise` | `other`, `peer-review`, `paratext`, `reference-entry`, `supplementary-materials`, `conference-abstract` | Hors headline par défaut |

La composition exacte est un paramètre versionné. Les flux ne sont jamais additionnés sans conserver leur ventilation.

### 5.4 Mesure Mines sur `published_core`

En mode `lineage`, 2020–2026-H1 :

- 9 437 œuvres dans `published_core` ;
- 9 364 possèdent un `primary_topic`, soit environ 99,2 % ;
- 7 132 possèdent un abstract, soit environ 75,6 %.

Le filtre d'abstract éliminerait donc environ un quart de la population alors que la quasi-totalité reste exploitable pour l'analyse des topics.

## 6. Axe topic et comptage

### 6.1 Axe canonique

```text
topic_axis = primary_topic.id
```

Le détecteur utilise un seul topic par œuvre afin que :

- la somme des comptes de topics soit égale au nombre d'œuvres classifiées ;
- une œuvre ne gonfle pas plusieurs séries ;
- les parts de portefeuille soient interprétables.

Les `topics` secondaires sont réservés à des détecteurs ultérieurs de ponts et transferts.

### 6.2 Identité

Clé : ID court OpenAlex, par exemple `T10005`.

Les champs suivants sont des métadonnées observées :

- `display_name` ;
- `subfield` ;
- `field` ;
- `domain` ;
- `created_date` ;
- `updated_date`.

Un changement de libellé ne crée pas un nouveau topic.

### 6.3 Topics absents

Les œuvres dont `primary_topic` est absent :

- restent dans les métriques de couverture ;
- ne contribuent à aucune série de topic ;
- sont comptées dans `unclassified_count` ;
- peuvent réduire la confiance si leur part varie fortement.

### 6.4 Dénominateurs

Conserver deux totaux par bucket :

- `included_works_count` : toutes les œuvres du flux ;
- `classified_works_count` : œuvres possédant un `primary_topic`.

La part de portefeuille d'un topic est :

```text
topic_share = topic_count / classified_works_count
```

La couverture est :

```text
topic_coverage = classified_works_count / included_works_count
```

### 6.5 Mode de comptage institutionnel

Version POC : `full_counting`.

Une œuvre incluse compte une fois, quel que soit le nombre d'auteurs ou d'affiliations Mines. Les doublons d'affiliation ne la multiplient pas.

Une analyse fractionnaire pourra être ajoutée ultérieurement comme sensibilité, mais ne doit pas remplacer silencieusement le comptage entier.

### 6.6 Détection multi-échelle et corroboration hiérarchique (v0.2)

Le comptage canonique reste `primary_topic.id`. Mais chaque œuvre porte déjà, dans
son payload, la chaîne complète `topic → subfield → field → domain`. Le détecteur
agrège donc les mêmes séries mensuelles aux niveaux **subfield** et **field**
(somme gratuite et hors ligne des topics enfants) et applique à l'identique le
classificateur déterministe des sections 12–13 à chaque niveau.

Le subfield et le field ne remplacent pas le topic : ils fournissent une **couche
de corroboration**. Chaque `TopicMomentumSignal` reçoit un bloc
`scale_corroboration` :

```json
"scale_corroboration": {
  "subfield_direction": "RISING",
  "field_direction": "STABLE",
  "concordance": "CORROBORATED",
  "note": "ISOLATED_WITHIN_SUBFIELD | DIFFUSE_SUBFIELD_SHIFT | CONTRADICTED"
}
```

Règles de lecture :

| Configuration | `concordance` | Effet |
|---|---|---|
| Topic `RISING` et subfield parent `RISING` de même sens | `CORROBORATED` | Signal le plus fort ; contribue à la confiance |
| Subfield plat, topic `RISING` isolé | `ISOLATED_WITHIN_SUBFIELD` | Signal conservé, marqué comme émergence focalisée |
| Subfield `RISING` sans topic dominant | `DIFFUSE_SUBFIELD_SHIFT` | Carte de niveau subfield, pas de faux signal topic |
| Topic `RISING`, subfield en sens opposé | `CONTRADICTED` | Rétrogradé ; revue requise (artefact de petit effectif probable) |

`concordance` **ne recrée pas** un seuil : c'est une annotation dérivée des
directions déjà calculées à chaque niveau. Elle répond aux artefacts taxonomiques
de TM-08.2 (un pic 2→7 dans un topic incohérent dont le subfield ne bouge pas est
démoté automatiquement).

Justification chiffrée et arbitrage complet : `06_topic-granularity-diagnostic.md`.

### 6.7 Statistiques de petits effectifs

Au grain topic, les comptes de fenêtre sont typiquement dans `[1, 8]`. Deux garde-
fous, indépendants du niveau :

- **Borne de Poisson (v0.2)** : déclencher et afficher sur la borne inférieure de
  l'IC 95 % du rate ratio, pas sur le point estimé ; afficher `n (IC 95 %)`.
- **Shrinkage empirique-bayésien (v0.3, différé)** : taux du topic tiré de la
  distribution de son subfield ; signal sur la déviation postérieure. Version
  principielle de la borne de Poisson, qui utilise la hiérarchie au lieu d'y monter.

## 7. Temporalité et fenêtres

### 7.1 Grain de stockage

```text
bucket_granularity = month
```

Le mois permet de reconstruire ensuite des trimestres, semestres, années et fenêtres glissantes sans relancer la collecte historique.

### 7.2 Fenêtre de signal

Valeurs POC :

```text
analysis_window_months = 12
evaluation_step_months = 3
history_min_months = 36
```

Les signaux sont évalués chaque trimestre sur une fenêtre glissante de douze mois. Cette combinaison :

- réduit la saisonnalité ;
- évite les comparaisons semestre/année ;
- reste assez réactive ;
- limite la sparsité des topics institutionnels.

### 7.3 Freeze initial

Pour un corpus arrêté au 30 juin 2026 :

- fenêtre courante : 2025-07-01 → 2026-06-30 ;
- fenêtre précédente : 2024-07-01 → 2025-06-30 ;
- historique : buckets mensuels depuis 2020-01-01.

### 7.4 Périodes incomplètes

- le mois courant incomplet n'entre pas dans la détection ;
- une période partielle peut être affichée comme `provisional`, jamais comparée sans annualisation ou fenêtre symétrique ;
- la date de coupure est conservée dans le signal ;
- toute donnée postérieure à la coupure est exclue d'un backtest.

## 8. Stratégie de requêtage OpenAlex

### 8.1 Principe à deux niveaux

#### Niveau A — census agrégé

Le headline peut être produit par des requêtes `group_by=primary_topic.id` pour chaque bucket mensuel. Aucun abstract ni texte intégral n'est téléchargé.

#### Niveau B — evidence fetch

Les œuvres détaillées sont récupérées uniquement pour :

- les topics signalés ;
- les fenêtres nécessaires au dossier ;
- les contrôles de qualité et exemples.

Cette séparation préserve le principe déjà validé par le claim-radar : calcul bon marché à grande échelle, enrichissement coûteux seulement après détection.

### 8.2 Requête de census — mode lineage

Forme logique :

```text
GET /works
filter=
  authorships.institutions.lineage:I70768539,
  from_publication_date:YYYY-MM-DD,
  to_publication_date:YYYY-MM-DD,
  type:article|review|conference-paper|book|book-chapter|data-paper|software-paper|report
group_by=primary_topic.id
per_page=200
cursor=*
corpus=core
```

### 8.3 Pagination obligatoire des groupes

Une réponse groupée retourne au maximum 200 groupes par page. Le client doit :

1. commencer par `cursor=*` ;
2. suivre `meta.next_cursor` jusqu'à `null` ;
3. agréger toutes les pages ;
4. traiter le groupe inconnu ;
5. vérifier que la somme des groupes, inconnu compris, correspond à `meta.count`.

Exemple mesuré sur la fenêtre juillet 2025–juin 2026 : la première page contient déjà 200 groupes, possède un `next_cursor` et ne représente que 434 des 1 142 œuvres correspondantes. Lire uniquement la première page produirait donc un headline faux.

### 8.4 Requête de couverture

La requête groupée doit conserver :

- `meta.count` comme total du flux ;
- le compte du groupe inconnu ;
- la somme des groupes classifiés ;
- le nombre de groupes ;
- `meta.x_query.oql` et `meta.x_query.oqo` si disponibles.

### 8.5 Requête d'evidence

Forme logique :

```text
GET /works
filter=
  <scope institutionnel>,
  primary_topic.id:Txxxxx,
  from_publication_date:YYYY-MM-DD,
  to_publication_date:YYYY-MM-DD,
  type:<published_core>
select=id,doi,display_name,publication_date,type,primary_topic,authorships,cited_by_count,updated_date
cursor=*
per_page=100
corpus=core
```

Le champ abstract n'est demandé que si un drill-down sémantique est déclenché. Le sous-corpus textuel est alors documenté séparément ; il ne remplace jamais le corpus du headline.

### 8.6 Classic filters, OQL et ambiguïté

Le code du détecteur utilise des colonnes explicites :

- `authorships.institutions.id` pour l'exact ;
- `authorships.institutions.lineage` pour le hiérarchique ;
- `authorships.institutions.ror` pour un ROR exact.

Une requête OQL formulée comme « institution is … » se traduit actuellement en colonne `authorships.institutions.lineage`. Le manifeste conserve donc les colonnes OQO produites par l'API et ne se contente jamais du texte naturel de la requête.

### 8.7 Corpus OpenAlex

```text
corpus = core
```

Le paramètre est écrit explicitement même s'il correspond au défaut actuel. Le corpus d'expansion XPAC n'est pas introduit silencieusement.

### 8.8 API live et reproductibilité

Une requête live reconstruit le passé avec l'état actuel d'OpenAlex. Elle ne représente pas nécessairement ce que la plateforme aurait observé historiquement.

Le manifeste distingue :

- `retrospective_snapshot` : historique recalculé depuis l'état courant ;
- `observed_vintage` : snapshot réellement persisté à la date du sweep.

Le backtest POC fondé sur une extraction live doit être qualifié de **retrospective simulation**, sauf si des snapshots historiques ont été archivés.

### 8.9 Stratégie de sync

#### POC et offre légère

- relancer les census agrégés ;
- persister chaque résultat ;
- refaire périodiquement un census complet du petit sous-ensemble institutionnel ;
- comparer les réponses et journaliser les révisions.

#### Production avec service OpenAlex adapté

- utiliser `from_updated_date` pour upserter les œuvres modifiées ;
- recalculer les agrégats affectés ;
- réconcilier périodiquement les suppressions et fusions ;
- conserver le manifeste ou la date du snapshot.

Les filtres de sync continus et snapshots quotidiens relèvent actuellement des offres payantes OpenAlex ; le snapshot public est trimestriel. L'architecture ne doit donc pas promettre une fraîcheur quotidienne sans préciser le mode d'accès.

## 11. Construction des séries

Pour chaque `topic_id` :

1. trier tous les buckets mensuels ;
2. compléter les mois absents par zéro ;
3. calculer les fenêtres glissantes de douze mois ;
4. n'évaluer qu'un point tous les trois mois ;
5. conserver simultanément counts et shares ;
6. marquer les fenêtres dont la couverture ou le périmètre a changé.

Notations :

- `c0` : count de la fenêtre courante ;
- `c1` : count de la fenêtre précédente de même durée ;
- `c2` : count de la fenêtre encore antérieure ;
- `C0`, `C1` : totaux classifiés correspondants ;
- `s0 = c0/C0`, `s1 = c1/C1` ;
- `h` : total historique avant la fenêtre précédente.

---

## 12. Mesures calculées

### 12.1 Delta absolu

```text
count_delta = c0 - c1
```

### 12.2 Ratio de taux lissé

```text
count_rate_ratio = (c0 + 0.5) / (c1 + 0.5)
```

Le lissage évite les divisions par zéro mais le statut de présence conserve l'information exacte `c1=0`.

### 12.3 Part de portefeuille

```text
share_delta = s0 - s1
share_rate_ratio = (s0 + epsilon) / (s1 + epsilon)
```

`epsilon` est versionné et uniquement utilisé pour le calcul numérique.

### 12.4 Croissance et accélération

```text
growth_now = log((c0 + 0.5) / (c1 + 0.5))
growth_before = log((c1 + 0.5) / (c2 + 0.5))
acceleration_value = growth_now - growth_before
```

### 12.5 Baseline historique

Sur les fenêtres de douze mois antérieures à la fenêtre courante :

- médiane historique du count ;
- médiane historique de la share ;
- MAD de la share ;
- percentile empirique de la valeur courante ;
- pente robuste de la share, calculée si le nombre de points est suffisant.

Le percentile et la pente ne déclenchent pas seuls un signal dans la version 0.1 ; ils l'expliquent et contribuent à la confiance.

## 13. Classification en trois axes

### 13.1 `presence_status`

| Valeur | Règle |
|---|---|
| `NEW` | `c0 >= min_current`, `c1 = 0`, aucune présence historique suffisante |
| `REACTIVATED` | `c0 >= min_current`, `c1 = 0`, présence historique `h >= min_history` |
| `PERSISTING` | `c0 > 0` et `c1 > 0` |
| `DORMANT` | `c0 = 0` et `c1 >= min_previous` |
| `INTERMITTENT` | alternance de présence/absence sans direction soutenue |
| `INSUFFICIENT` | support trop faible pour interprétation |

Si le topic OpenAlex a été créé ou profondément modifié pendant la période de baseline, ajouter `taxonomy_change=true` et abaisser la confiance.

### 13.2 `momentum_direction`

#### `RISING`

Toutes les conditions POC :

- `count_delta >= min_abs_delta` ;
- `count_rate_ratio >= rise_count_ratio` ;
- `share_rate_ratio >= rise_share_ratio` ;
- `active_months_current >= min_active_months` ;
- support minimal satisfait.

#### `FALLING`

Conditions symétriques :

- `count_delta <= -min_abs_delta` ;
- `count_rate_ratio <= fall_count_ratio` ;
- `share_rate_ratio <= fall_share_ratio` ;
- support minimal satisfait dans la fenêtre précédente.

#### `STABLE`

Les seuils rising/falling ne sont pas franchis et le support est suffisant.

#### `UNDETERMINED`

Support, couverture ou stabilité du périmètre insuffisants.

### 13.3 `growth_mode`

| Valeur | Sens |
|---|---|
| `ABSOLUTE_AND_PORTFOLIO` | counts et part vont dans le même sens |
| `ABSOLUTE_ONLY` | volume en hausse mais part stable/baisse |
| `PORTFOLIO_ONLY` | part en hausse avec volume peu modifié |
| `CONTRADICTORY` | counts et part évoluent en sens opposé |
| `NONE` | aucun mouvement significatif |

Seul `ABSOLUTE_AND_PORTFOLIO` peut produire directement un signal `RISING` de confiance haute dans la version POC.

### 13.4 `acceleration_status`

| Valeur | Règle |
|---|---|
| `ACCELERATING` | la variation de croissance renforce la direction courante au-delà de `acceleration_epsilon` |
| `SLOWING` | elle réduit la force de la direction |
| `STEADY` | variation dans la zone neutre |
| `NA` | moins de trois fenêtres ou direction non interprétable |

## 15. Confiance

### 15.1 Dimensions

- `sample_support` : counts et activité mensuelle ;
- `coverage` : proportion d'œuvres classifiées ;
- `temporal_consistency` : direction retrouvée sur plusieurs évaluations ;
- `window_completeness` : fenêtres complètes et symétriques ;
- `scope_stability` : même version d'univers et même liste d'institutions ;
- `taxonomy_stability` : topic antérieur à la baseline et metadata stable ;
- `parameter_stability` : direction stable sous plusieurs seuils raisonnables.

### 15.2 Niveaux

#### `HIGH`

- fenêtres complètes ;
- couverture ≥ 95 % ;
- au moins 12 œuvres sur l'historique utile ;
- au moins 5 dans la fenêtre qui porte le signal ;
- direction soutenue sur au moins deux évaluations ;
- univers et topic stables ;
- sens du signal stable dans l'analyse de sensibilité.

#### `MEDIUM`

- couverture ≥ 90 % ;
- au moins 6 œuvres historiques ;
- au moins 3 dans la fenêtre pertinente ;
- fenêtre complète ;
- pas d'alerte majeure de taxonomie ou de périmètre.

#### `LOW`

- signal calculable mais petit échantillon, direction unique ou sensibilité forte.

#### `VERY_LOW`

- période incomplète, topic nouvellement créé, changement de périmètre non résolu ou couverture insuffisante.

Les signaux `LOW/VERY_LOW` restent consultables en mode exploratoire mais ne déclenchent pas d'alerte par défaut.

## 17. Dossier de preuves minimal

Le signal est accompagné d'une vue ou d'un document contenant :

1. topic ID et libellé ;
2. périmètre institutionnel utilisé ;
3. flux documentaire ;
4. counts et parts courant/précédent ;
5. série historique ;
6. raison exacte du franchissement de seuil ;
7. niveau et raisons de confiance ;
8. couverture topic ;
9. principales œuvres des deux fenêtres ;
10. avertissements sur taxonomie, fenêtre, périmètre ou indexation ;
11. lien vers le manifeste de requête.

### Sélection des œuvres représentatives

La version POC peut combiner :

- œuvres les plus récentes ;
- œuvres les plus citées, avec prudence sur l'âge ;
- diversité de sous-unités/auteurs ;
- au moins un exemple de chaque fenêtre.

La sélection est une aide à la lecture ; elle n'intervient pas dans le déclenchement du signal.

## 18. Invariants et validations automatiques

### Invariants de collecte

- toutes les pages `group_by` ont été consommées ;
- `sum(topic_counts) + unclassified_count == included_works_count` ;
- aucun topic n'est identifié uniquement par son label ;
- aucun abstract n'est requis pour le census ;
- toutes les fenêtres d'une comparaison ont la même durée ;
- le mois incomplet n'est pas inclus ;
- les paramètres `corpus`, types et scope sont explicites ;
- une œuvre ne compte qu'une fois dans un bucket de `primary_topic`.

### Invariants de signal

- `RISING` exige un count et une part allant dans le même sens pour la confiance haute ;
- `NEW` ne signifie jamais que le topic est nouveau dans OpenAlex ;
- `DORMANT` exige un support antérieur minimal ;
- `ACCELERATING` exige au moins trois fenêtres comparables ;
- un changement de version d'univers interdit la continuité silencieuse ;
- une modification de taxonomie est signalée comme telle ;
- toute interprétation renvoie au JSON calculé.

### Conditions d'échec du run

- pagination incomplète ;
- somme des groupes incohérente ;
- résolution ROR ambiguë ou absente ;
- fenêtre inversée ou incomplète non déclarée ;
- couverture sous un seuil critique configurable ;
- absence de Query Manifest ;
- collision d'un même `topic_id` avec des hiérarchies incompatibles dans le même vintage.

## 19. Tests d'acceptation

### A. Requêtage

- [ ] `exact`, `lineage` et `curated_set` produisent trois manifestes distincts ;
- [ ] le ROR exact et l'OpenAlex ID exact produisent le même corpus ;
- [ ] le lineage inclut l'entité racine et les descendants archivés ;
- [ ] l'API groupée est paginée jusqu'à `next_cursor=null` ;
- [ ] le groupe inconnu est compté ;
- [ ] `has_abstract` n'apparaît pas dans la requête de census ;
- [ ] `corpus=core` est explicite.

### B. Agrégation

- [ ] la somme des topics classifiés correspond au total classifié ;
- [ ] les mois sans topic créent un zéro ;
- [ ] une œuvre multi-affiliée ne compte qu'une fois ;
- [ ] le libellé peut changer sans casser la série si l'ID reste le même ;
- [ ] deux topics de même nom mais d'IDs différents restent distincts.

### C. Temporalité

- [ ] 2025-07→2026-06 est comparé à 2024-07→2025-06 ;
- [ ] 2026-H1 n'est pas comparé brut à 2025 ;
- [ ] une date de coupure de backtest exclut toutes les données ultérieures ;
- [ ] une fenêtre partielle produit `is_complete=false` et une confiance dégradée.

### D. Classification

- [ ] un topic absent historiquement et suffisamment actif devient `NEW` ;
- [ ] un topic ancien revenant après absence devient `REACTIVATED` ;
- [ ] une hausse de count avec part en baisse devient `ABSOLUTE_ONLY` ou `CONTRADICTORY`, pas `RISING/HIGH` ;
- [ ] un topic passant de 1 à 2 œuvres reste sous le support minimal ;
- [ ] une disparition après un count antérieur suffisant devient `DORMANT` ;
- [ ] l'accélération est `NA` avec moins de trois fenêtres.

### E. Confiance

- [ ] un topic OpenAlex créé pendant la baseline est dégradé ;
- [ ] une couverture inférieure à 90 % empêche la confiance haute ;
- [ ] un changement de scope versionne l'univers ;
- [ ] le signal conserve les résultats du test de sensibilité des seuils.

### F. Compatibilité

- [ ] une vue dérivée peut reproduire `topic_delta_table` avec des fenêtres homogènes ;
- [ ] le nouveau JSON alimente le feed et le Signal Dossier ;
- [ ] le drill-down claims reste facultatif et séparé ;
- [ ] aucun composant ne dépend des labels pour le threading.
